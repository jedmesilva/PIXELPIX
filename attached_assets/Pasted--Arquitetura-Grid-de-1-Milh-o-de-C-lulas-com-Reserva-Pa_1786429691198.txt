# Arquitetura: Grid de 1 Milhão de Células com Reserva, Pagamento e Prêmios

> **v2** — incorpora três correções de segurança: rate limit reforçado com `device_id`
> e escalonamento para CAPTCHA (seção 3.1), proibição explícita de token em URL
> (seção 6), e idempotência na criação de cobrança Pix (seção 4.3.1).

Este documento explica a lógica de estrutura para um grid de células (estilo "pixel war")
onde usuários revelam células bloqueadas, passam por um checkout de pagamento, e podem
ganhar prêmios sorteados pelo servidor.

---

## 1. Identificação da célula

Cada célula tem um **id numérico único e estável**, de `0` a `999.999`. Esse id nunca
muda, independente de como o grid é exibido na tela.

- **Não é necessário numerar visualmente** as células para o usuário — o número é
  apenas um dado interno que trafega entre front e back.
- Em telas responsivas, o número de colunas visíveis (`columns`) pode variar (ex: 20
  colunas no mobile, 45 no desktop). Isso é só um detalhe de **layout/renderização**.
- O `id` lógico da célula é calculado a partir de `row` e `col` **apenas para saber onde
  desenhar** o quadradinho na tela:

```js
const id = row * columns + col; // usado só para renderizar/posicionar
```

- No banco de dados, a chave de verdade é o **`id` único**, não `row`/`col` — porque
  `row`/`col` dependem de `columns`, que muda por tela. `id` não muda nunca.

```sql
CREATE TABLE cells (
  id INT PRIMARY KEY,   -- 0 a 999999, estável em qualquer resolução de tela
  ...
);
```

### 1.1 ⚠️ Bug identificado na implementação atual (`PixelGrid.jsx`)

O protótipo atual **viola o princípio acima**. Hoje o `id` é calculado assim:

```js
// implementação atual — INCORRETA
const cols = Math.max(1, Math.floor(width / MIN_CELL_PX)); // varia por tela
...
const id = row * columns + col; // usa "columns" que muda por tela
```

`columns` é derivado da largura do viewport (`width / MIN_CELL_PX`), então o número de
colunas visíveis muda entre dispositivos — por exemplo, 20 colunas no mobile, 45 no
desktop. Como o `id` é calculado com esse valor variável, **a mesma célula física pode
receber números diferentes dependendo do tamanho da tela** em que é exibida ou clicada.

Isso é usado tanto para posicionar a célula na tela (`top: row * cellSize, left: col *
cellSize`) quanto para gerar o número exibido no modal de detalhe:

```jsx
<span style={styles.sheetEyebrow}>
  Pixel #{detail.id.toLocaleString("pt-BR")}
</span>
```

**Por que isso é um problema real, não só teórico:** se um usuário reserva uma célula no
desktop e depois abre o mesmo link no celular (ou só redimensiona a janela), o id
mostrado — e potencialmente enviado numa reserva — pode não corresponder à mesma célula
física. Isso quebra a premissa de id estável que sustenta toda a lógica de reserva,
token e webhook descrita nas seções 3 e 4.

#### Correção necessária

Separar **duas geometrias diferentes**, que hoje estão fundidas numa só variável:

1. **Geometria visual** (`visualColumns`) — quantas colunas cabem na tela agora. Pode e
   deve continuar variando por dispositivo; é só o que decide onde desenhar cada célula
   na tela (`top`/`left`). Não deve influenciar o `id`.

2. **Geometria lógica** (`LOGICAL_COLUMNS`) — uma constante fixa, que nunca muda,
   independente de tela. É ela que deve ser usada para calcular o `id` da célula.

```js
// proposta — CORRETA
const LOGICAL_COLUMNS = 1000; // fixo, compartilhado entre front e back, nunca muda

// geometria visual: só decide layout/posicionamento na tela atual
const visualColumns = Math.max(1, Math.floor(width / MIN_CELL_PX));

// geometria lógica: decide o id — independente da tela
const id = logicalRow * LOGICAL_COLUMNS + logicalCol;
```

Com `LOGICAL_COLUMNS` fixo, a célula "linha 6, coluna 30" é sempre `id = 6030`,
não importa se o dispositivo mostra 20, 45 ou 100 colunas por vez na tela. O `visualColumns`
continua livre para variar por viewport — isso não afeta a UX responsiva já existente,
afeta só o cálculo do identificador.

#### Onde essa fórmula roda: front, não back

O cálculo `id = row × LOGICAL_COLUMNS + col` acontece **no front**, no momento do
clique/reserva — não no backend. O front calcula o `id` usando a constante fixa e o
envia pronto na requisição de reserva (seção 4.2):

```js
// front — calcula o id e envia pronto
const id = logicalRow * LOGICAL_COLUMNS + logicalCol;
POST /api/cells/reserve { id }
```

O **back nunca recalcula** `row`/`col`/`columns` a partir de nada — ele recebe o `id`
como um valor opaco e o usa diretamente como chave primária (`INSERT ... WHERE id =
$1`). A responsabilidade do back é ser a autoridade sobre **disponibilidade** daquele
id (se já está reservado, pago, expirado), nunca sobre **qual é o id correto** de uma
célula — isso é definido inteiramente pela fórmula fixa do lado do front.

Essa distinção importa porque `LOGICAL_COLUMNS` precisa ser a mesma constante nos dois
lados (front e, se algum dia o back também precisar derivar `row`/`col` a partir de um
`id` — por exemplo, para preencher um mapa visual de estatísticas —, ele deve usar o
valor inverso da mesma constante, nunca uma geometria diferente).

**Escopo da correção:** como ainda não existe backend nem reservas gravadas — só o
protótipo de front (`PixelGrid.jsx`) —, essa é uma correção simples de aplicar agora,
sem necessidade de migração de dados. O ideal é corrigir antes de implementar o back
(seções 3 e 4), para que a API já nasça usando a fórmula de `id` correta e estável.

## 2. Por que não pré-popular 1 milhão de linhas

Como os prêmios são decididos **no momento do clique** (não existem de antemão), não há
necessidade de já ter 1 milhão de registros no banco desde o início.

- **Abordagem esparsa (recomendada neste caso):** o registro só é criado quando a célula
  é clicada/reservada. Economiza espaço e evita 1 milhão de inserts de setup.
- **Pré-popular faria sentido** apenas se o conteúdo de cada célula já fosse definido
  antes de qualquer clique (ex: um mapa fixo gerado no início). Não é o caso aqui.

### 2.1 Consequência: como o front sabe o status de uma célula

Como a tabela é esparsa, **ausência de linha = célula disponível**. O endpoint que
alimenta o grid virtualizado precisa refletir isso explicitamente, e não pode assumir
que "não retornou nada" é um erro:

```js
// GET /api/cells?from=1000&to=1500
app.get('/api/cells', async (req, res) => {
  const { from, to } = req.query;

  const rows = await db.query(
    `SELECT id, status FROM cells WHERE id BETWEEN $1 AND $2`,
    [from, to]
  );

  const existing = new Map(rows.rows.map(r => [r.id, r.status]));

  // preenche o range inteiro — ids sem linha no banco = 'available'
  const result = [];
  for (let id = from; id <= to; id++) {
    result.push({ id, status: existing.get(id) ?? 'available' });
  }

  res.json(result);
});
```

- O front pede por **range de ids** (equivalente ao "chunk" que o grid virtualizado
  já busca por scroll), nunca célula por célula.
- Células com status `expired` devem ser tratadas como `available` na resposta ao
  front — o usuário não precisa saber que alguém tentou e não pagou antes.
- Esse endpoint é somente leitura e pode (e deve) ser cacheado agressivamente por
  poucos segundos, já que a maior parte do grid muda pouco entre polls.

## 3. O problema da concorrência (race condition)

Se dois usuários clicarem na mesma célula quase ao mesmo tempo, é preciso garantir que
**só um consiga reservar/revelar** aquela célula.

### ❌ O que NÃO funciona

```js
// Tem uma brecha: entre o SELECT e o INSERT, outro request pode passar
const existe = await db.query('SELECT * FROM cells WHERE id = ?', [id]);
if (!existe) {
  await db.query('INSERT INTO cells (id, user_id) VALUES (?, ?)', [id, userId]);
}
```

Dois requests podem executar o `SELECT` simultaneamente, ambos verem "não existe", e
ambos tentarem o `INSERT`.

### ✅ O que funciona: `UNIQUE` + `ON CONFLICT DO NOTHING`

A garantia precisa vir do **banco de dados**, não da lógica da aplicação, porque o banco
processa a constraint `UNIQUE` de forma atômica — não existe zona cinzenta, mesmo que
dois requests cheguem no mesmo milissegundo.

```sql
INSERT INTO cells (id, user_id, status)
VALUES ($1, $2, 'reserved')
ON CONFLICT (id) DO NOTHING
RETURNING id;
```

- Se o `INSERT` **retornar uma linha** → esse request "ganhou a corrida".
- Se **não retornar nada** → outra pessoa já reservou essa célula (não importa se foi há
  1 hora ou 0,3ms atrás).

### 3.1 Abuso do endpoint de reserva

Reservar uma célula é uma ação "grátis" do ponto de vista do usuário — não exige
pagamento nem e-mail ainda. Isso abre espaço para abuso: um script pode reservar
continuamente as células mais desejáveis (ex: as do centro do grid) e deixá-las expirar
de propósito, travando-as por 5 minutos repetidamente e impedindo outros usuários de
sequer tentar.

⚠️ **Correção:** rate limit só por IP é insuficiente sozinho. Um atacante com proxy
residencial rotativo ou VPN troca de IP a cada request e contorna qualquer limite
baseado só nesse sinal — na prática, cada tentativa "nova" chega como se fosse um
usuário diferente. IP continua sendo a primeira linha de defesa (é gratuito, já vem em
toda requisição), mas precisa ser combinado com um segundo sinal mais caro de forjar, e
com um mecanismo de escalonamento quando o padrão sugerir abuso coordenado.

- **Sinal primário — IP:**
  - Rate limit por IP no total de reservas ativas simultâneas (teto curto, tipo 3–5).
  - Rate limit por IP no total de tentativas por minuto, independente de sucesso —
    evita varredura sequencial de ids.
- **Sinal secundário — `device_id` (fingerprint de front, ex: FingerprintJS):**
  - Capturado no momento do clique em "Revelar" e enviado junto com o `POST
    /api/cells/reserve` (não só depois, no checkout — ver seção 8.4).
  - Aplicar o mesmo teto de reservas ativas simultâneas **por `device_id`**, além do
    teto por IP. Um `device_id` que reaparece atrás de IPs diferentes num curto
    intervalo é o padrão típico de VPN rotativa, e é esse cruzamento que o rate limit
    por IP sozinho não enxerga.
  - `device_id` é um sinal probabilístico (pode ser resetado, spoofado com esforço
    maior) — não substitui o IP, soma-se a ele. A combinação dos dois eleva o custo do
    ataque sem exigir conta de usuário.
- **Escalonamento — CAPTCHA:**
  - Quando o mesmo `device_id` ou faixa de IPs ultrapassar os tetos acima repetidas
    vezes numa janela curta (ex: 3 rate-limits acionados em 10 minutos), o próximo
    `POST /api/cells/reserve` desse `device_id`/IP passa a exigir um desafio CAPTCHA
    resolvido antes de a reserva ser aceita.
  - Isso evita exigir CAPTCHA de todo mundo (ruim para conversão) e reserva o atrito
    só para o padrão que já demonstrou comportamento de abuso.

⚠️ **Correção:** IP e `device_id` cobrem o caso de um mesmo sinal se repetir. Mas um
atacante com proxies residenciais rotativos **e** perfis de navegador descartáveis
(incógnito, containers, reset de fingerprint) pode trocar os dois juntos a cada
request — cada tentativa passa como "usuário novo" nos dois contadores
simultaneamente, porque nenhum dos dois é reutilizado o bastante pra acionar o
próprio limite individual. Rate limit por contador não pega esse padrão; é preciso
uma camada de detecção que olhe o **comportamento agregado**, não sinais isolados:

- **Detecção por padrão comportamental** (job assíncrono ou regra em stream, não
  bloqueia o request em si):
  - Volume de reservas por faixa de IP/ASN (subnet ou provedor de rede) num período
    curto, mesmo que cada IP individual dentro da faixa fique abaixo do teto —
    proxies residenciais tendem a se agrupar em blocos de ASN conhecidos.
  - Velocidade de reserva incompatível com uso humano (ex: múltiplas células
    reservadas em menos de 1–2 segundos entre cliques).
  - Concentração anormal de reservas nas mesmas células "desejáveis" (ex: região
    central do grid) vindas de `device_id`s nunca vistos antes, dentro de uma janela
    curta — esse é o padrão específico de quem está tentando travar posições
    valiosas, não só reservar ao acaso.
  - Quando esse job identificar um cluster suspeito, a ação recomendada é a mesma
    escalada de CAPTCHA acima, mas aplicada à faixa de IP/ASN inteira, não só a um
    IP ou `device_id` isolado — é a única forma de responder a rotação coordenada
    dos dois sinais ao mesmo tempo.
  - Esse tipo de detecção normalmente já vem embutido em serviços de proteção de
    borda (ex: Cloudflare Bot Management, AWS WAF com regras gerenciadas) — vale
    avaliar isso antes de construir a lógica de clustering do zero.
- Isso é defesa de infraestrutura (proxy/API gateway ou middleware), não muda a lógica
  de concorrência do banco descrita acima — as camadas são complementares.

## 4. Sem autenticação: token de reserva

O sistema não tem login/conta de usuário. O usuário só informa um **e-mail** durante o
checkout, e é para esse e-mail que um certificado é enviado após o pagamento confirmado.

Isso muda como identificamos "de quem" é uma reserva: em vez de um `user_id` vinculado a
uma conta, cada reserva recebe um **token aleatório** (UUID), gerado pelo servidor no
momento do clique. Esse token não é autenticação de conta — é uma chave temporária que
prova que uma requisição posterior (informar e-mail, confirmar pagamento) pertence à
mesma reserva que originou o clique.

Sem esse token, qualquer pessoa poderia, em teoria, chamar a API tentando confirmar ou
associar um e-mail a uma célula que não foi ela quem reservou.

### 4.1 Estrutura da tabela

```sql
CREATE TABLE cells (
  id INT PRIMARY KEY,
  reservation_token UUID NOT NULL DEFAULT gen_random_uuid(),
  email TEXT,                              -- preenchido na etapa de e-mail
  status TEXT NOT NULL DEFAULT 'reserved',
  -- reserved | paid_pending_prize | paid | expired
  reserved_at TIMESTAMP DEFAULT NOW(),
  payment_id TEXT UNIQUE,                  -- garante idempotência do webhook
  prize_id INT,
  certificate_sent_at TIMESTAMP
);
```

> O status `paid_pending_prize` foi adicionado na seção 4.4 — é o que resolve o
> problema de não-atomicidade descrito abaixo.

### 4.2 Passo 1 — Clique: tenta reservar

⚠️ **Correção:** a versão abaixo substitui a query original. A versão original usava
apenas `ON CONFLICT (id) DO NOTHING`, que cobre só o caso de célula nunca tocada — para
uma célula **expirada**, já existe uma linha com aquele `id`, então `DO NOTHING` não
faz nada e o endpoint erroneamente responde "célula indisponível" para uma célula que na
verdade podia (e devia) ser reaberta. A query correta trata os dois casos numa só
chamada, sempre:

```js
const result = await db.query(
  `INSERT INTO cells (id, status)
   VALUES ($1, 'reserved')
   ON CONFLICT (id) DO UPDATE
     SET reservation_token = gen_random_uuid(),
         email = NULL,
         status = 'reserved',
         reserved_at = NOW()
   WHERE cells.status = 'expired'
   RETURNING id, reservation_token`,
  [id]
);

if (result.rows.length === 0) {
  return { error: 'Célula já reservada ou revelada' };
}

const { reservation_token } = result.rows[0];
return { cellId: id, token: reservation_token };
```

- Se a célula **nunca existiu** → o `INSERT` puro cria a linha, retorna normalmente.
- Se a célula está **`expired`** → o `ON CONFLICT DO UPDATE ... WHERE status = 'expired'`
  reabre com um **novo** `reservation_token` (invalidando qualquer token antigo que o
  usuário anterior, que não pagou, ainda tivesse guardado), e retorna normalmente.
- Se a célula está **`reserved`**, **`paid_pending_prize`** ou **`paid`** → a cláusula
  `WHERE cells.status = 'expired'` não bate, o `UPDATE` não altera nada, e o `RETURNING`
  não devolve linha — o endpoint responde "célula já reservada ou revelada", como
  esperado.

A partir do momento em que a linha é criada ou reaberta, a constraint `UNIQUE` do `id`
impede que qualquer outra pessoa reserve essa mesma célula — a disputa já foi resolvida.
O `token` retornado é guardado pelo front (em memória / estado da aplicação) e enviado
em toda requisição seguinte relacionada a essa reserva — **sempre no corpo da
requisição, nunca em URL** (ver seção 6).

> A antiga seção "4.6 Reabertura de célula expirada" foi incorporada aqui — não existe
> mais uma query separada para reabertura; é a mesma chamada usada em todo clique de
> "Revelar", célula nova ou expirada.

### 4.3 Passo 2 — Usuário informa o e-mail

```js
const result = await db.query(
  `UPDATE cells SET email = $1
   WHERE id = $2 AND reservation_token = $3 AND status = 'reserved'
   RETURNING id`,
  [email, cellId, token]
);

if (result.rows.length === 0) {
  return { error: 'Reserva inválida, expirada ou token incorreto' };
}

const checkoutUrl = await criarCheckout(cellId, token);
return { checkoutUrl };
```

O `WHERE ... AND reservation_token = $3` garante que só quem tem o token certo (quem
realmente clicou naquela célula) consegue associar um e-mail a ela.

#### 4.3.1 Como o `token` chega de volta no webhook — e idempotência da cobrança

O webhook (seção 4.4) usa `req.body.token` como se ele viesse pronto no payload — mas
isso só funciona se o token for **embutido na cobrança Pix no momento da criação**, e o
provedor o devolver de volta no payload do webhook. Isso não acontece sozinho; precisa
ser configurado explicitamente em `criarCheckout`.

⚠️ **Correção:** a versão original de `criarCheckout` criava uma cobrança nova a cada
chamada, sem checar se já existia uma em aberto para aquela reserva. Como o endpoint
`POST /api/cells/email` (seção 4.3) não muda o `status` da célula ao gravar o e-mail —
ele continua `reserved` — nada impedia uma segunda chamada (refresh da página, duplo
clique no botão, retry de rede) de cair de novo em `criarCheckout(cellId, token)` e
gerar uma **segunda cobrança Pix** para a mesma célula. Isso confunde o usuário (dois
QR codes/links diferentes para a mesma reserva) e abre espaço para o caso em que ele
paga os dois por engano. A versão corrigida verifica primeiro se já existe uma cobrança
`pending` para aquele `cellId` + `token`, e reaproveita o checkout existente em vez de
criar outro:

```js
async function criarCheckout(cellId, token) {
  // idempotência: se já existe uma cobrança pendente para essa reserva,
  // reaproveita em vez de criar uma nova
  const existente = await db.query(
    `SELECT provider_payment_id, checkout_url
     FROM payments
     WHERE cell_id = $1 AND status = 'pending'
     ORDER BY created_at DESC
     LIMIT 1`,
    [cellId]
  );

  if (existente.rows.length > 0) {
    return existente.rows[0].checkout_url;
  }

  const cobranca = await provedorPix.criarCobranca({
    valor: PRECO_CELULA,
    // campo de referência externa — cada provedor tem o seu nome pra isso
    // (ex: "externalReference" no Asaas, "metadata" no Stripe)
    referenciaExterna: JSON.stringify({ cellId, token }),
  });

  await db.query(
    `INSERT INTO payments (cell_id, provider_payment_id, amount_cents, status, checkout_url)
     VALUES ($1, $2, $3, 'pending', $4)`,
    [cellId, cobranca.paymentId, PRECO_CELULA, cobranca.checkoutUrl]
  );

  return cobranca.checkoutUrl;
}
```

- A checagem é por `cell_id` + `status = 'pending'`, não por `token` — o token já foi
  validado na etapa anterior (`UPDATE ... WHERE reservation_token = $3`), então
  qualquer cobrança pendente associada àquele `cell_id` nesse ponto do fluxo pertence
  legitimamente à mesma reserva.
- Isso exige a coluna `checkout_url` na tabela `payments` (adicionada na seção 8.4)
  para poder devolver a mesma URL sem chamar o provedor de novo.
- Se a cobrança pendente já tiver expirado do lado do provedor (prazo próprio do Pix,
  geralmente mais curto que os 5 minutos de reserva), o provedor normalmente rejeita o
  pagamento no ato — o usuário simplesmente cai no fluxo de reserva expirada da seção
  4.5 no próximo tentativa de clique. Não é necessário tratamento adicional aqui.

No webhook, o `cellId` e o `token` são extraídos dessa referência externa devolvida
pelo provedor — não de um campo arbitrário que o provedor "por acaso" tenha:

```js
app.post('/webhook/payment-confirmed', async (req, res) => {
  // ...validação de assinatura...

  const { cellId, token } = JSON.parse(req.body.referenciaExterna);
  const paymentId = req.body.paymentId;
  // ...segue igual à seção 4.4.3...
});
```

Vale checar a documentação do provedor Pix escolhido (Asaas, por exemplo) para
confirmar o nome exato do campo de referência externa e o formato em que ele é
devolvido no payload do webhook — isso varia por provedor e precisa ser validado antes
de implementar.

### 4.4 Passo 3 — Pagamento confirmado via webhook

O pagamento **nunca deve ser confirmado pelo retorno direto do front** (ex: redirecionamento
de sucesso) — sempre por um webhook do provedor de pagamento, que é a fonte confiável.

#### 4.4.1 Validar a assinatura antes de processar qualquer coisa

O `req.body` de um endpoint público não é confiável só porque a URL é
`/webhook/payment-confirmed`. Sem verificar a assinatura HMAC que o provedor envia,
qualquer pessoa pode forjar essa chamada e "confirmar" um pagamento que nunca aconteceu.

```js
const crypto = require('crypto');

function verificarAssinaturaWebhook(rawBody, signatureHeader, secret) {
  const esperado = crypto
    .createHmac('sha256', secret)
    .update(rawBody)
    .digest('hex');

  // comparação em tempo constante — evita timing attack
  return crypto.timingSafeEqual(
    Buffer.from(esperado),
    Buffer.from(signatureHeader || '')
  );
}
```

O handler deve rejeitar a requisição (`401`) **antes** de tocar no banco se a assinatura
não bater. A maioria dos provedores (Stripe, Asaas, etc.) documenta o header específico
e o formato exato da assinatura — vale conferir a doc do provedor escolhido em vez de
assumir um formato genérico.

#### 4.4.2 O problema: múltiplas escritas não-atômicas

A versão original do fluxo fazia isso em passos soltos:

```
UPDATE status = 'paid'
   ↓
sortearPremio()
   ↓
UPDATE prize_id
   ↓
enviarCertificadoPorEmail()
   ↓
UPDATE certificate_sent_at
```

Se o processo cair (crash, deploy, timeout) entre o primeiro `UPDATE` e o resto, a
célula fica presa em `paid` **sem prêmio sorteado e sem certificado enviado** — e como
o webhook do provedor normalmente faz retry automático até receber `200 OK`, esse retry
bateria de novo no endpoint. Mas a query original filtra por `WHERE status = 'reserved'`,
que não é mais verdade depois do primeiro `UPDATE` — então o retry **não reprocessa
nada**, e a reserva fica travada permanentemente nesse estado intermediário quebrado.

#### 4.4.3 Solução: transação + estado intermediário + idempotência

⚠️ **Correção adicional:** a versão original filtrava só por `status = 'reserved'`. Isso
tem um buraco: se o pagamento for confirmado bem na borda dos 5 minutos, o job de
expiração (seção 4.5) pode rodar **antes** do webhook chegar, virando o status para
`expired`. Nesse caso, o `UPDATE ... WHERE status = 'reserved'` não encontra a linha, e
a versão original trataria isso como "já processado" — mas na verdade **o usuário pagou
de verdade** e a célula foi liberada por engano. A versão abaixo distingue esse caso de
uma duplicata legítima:

```js
app.post('/webhook/payment-confirmed', async (req, res) => {
  const rawBody = req.rawBody; // configurar o middleware pra preservar o body cru
  const assinaturaOk = verificarAssinaturaWebhook(
    rawBody,
    req.headers['x-webhook-signature'],
    process.env.WEBHOOK_SECRET
  );

  if (!assinaturaOk) {
    return res.status(401).send('Assinatura inválida');
  }

  const { cellId, paymentId, token } = req.body;

  const client = await pool.connect();
  try {
    await client.query('BEGIN');

    // aceita tanto 'reserved' quanto 'expired': se o token ainda bate, ninguém
    // reabriu a célula depois da expiração, então o pagamento ainda é válido
    const marcado = await client.query(
      `UPDATE cells
       SET status = 'paid_pending_prize', payment_id = $1
       WHERE id = $2 AND reservation_token = $3
         AND status IN ('reserved', 'expired')
       RETURNING email`,
      [paymentId, cellId, token]
    );

    if (marcado.rows.length === 0) {
      // não deu match — precisa distinguir duplicata (ok) de conflito real (não ok)
      const atual = await client.query(
        `SELECT payment_id FROM cells WHERE id = $1`,
        [cellId]
      );

      if (atual.rows[0]?.payment_id === paymentId) {
        // retry legítimo do provedor pra um pagamento já processado — idempotente
        await client.query('ROLLBACK');
        return res.status(200).send('OK');
      }

      // token não bate: a célula expirou E já foi reaberta/reservada por outra
      // pessoa antes desse webhook chegar. Não dá pra completar a reserva original
      // automaticamente sem risco de sobrescrever a reserva de quem reabriu —
      // fica registrado para revisão manual (provável reembolso).
      await client.query(
        `INSERT INTO webhook_events
           (payment_id, cell_id, payload, signature_valid, result)
         VALUES ($1, $2, $3, true, 'stale_token_conflict')`,
        [paymentId, cellId, JSON.stringify(req.body)]
      );
      await client.query('COMMIT');
      await alertarTimeDeOperacoesComLimite({ cellId, paymentId }); // fila de revisão manual, com limite

      return res.status(200).send('OK'); // aceita o webhook, mas não completa a reserva
    }

    const email = marcado.rows[0].email;
    const prize = sortearPremio();

    await client.query(
      `UPDATE cells SET status = 'paid', prize_id = $1 WHERE id = $2`,
      [prize.id, cellId]
    );

    // sincroniza a tabela payments dentro da mesma transação
    const pagamento = await client.query(
      `UPDATE payments SET status = 'confirmed', confirmed_at = NOW()
       WHERE provider_payment_id = $1
       RETURNING amount_cents`,
      [paymentId]
    );

    // entrada de caixa (receita) — mesma transação, nunca calculada depois via
    // agregação sobre payments (ver seção 9 para o porquê de um ledger dedicado)
    await client.query(
      `INSERT INTO cash_ledger (entry_type, cell_id, amount_cents)
       VALUES ('revenue', $1, $2)
       ON CONFLICT (entry_type, cell_id) DO NOTHING`,
      [cellId, pagamento.rows[0].amount_cents]
    );

    // saída de caixa (prêmio) — só grava se o prêmio tiver custo real;
    // "Sem prêmio" (value_cents = 0) não gera lançamento
    if (prize.value_cents > 0) {
      await client.query(
        `INSERT INTO cash_ledger (entry_type, cell_id, amount_cents)
         VALUES ('prize_payout', $1, $2)
         ON CONFLICT (entry_type, cell_id) DO NOTHING`,
        [cellId, prize.value_cents]
      );
    }

    await client.query('COMMIT');

    // envio de e-mail é I/O externo — fica fora da transação de propósito,
    // mas o estado 'paid' já está gravado e é a fonte de verdade
    await enviarCertificadoPorEmail(email, cellId, prize);
    await pool.query(
      `UPDATE cells SET certificate_sent_at = NOW() WHERE id = $1`,
      [cellId]
    );

    res.status(200).send('OK');
  } catch (err) {
    await client.query('ROLLBACK');
    res.status(500).send('Erro interno'); // provedor faz retry
  } finally {
    client.release();
  }
});
```

Pontos-chave dessa versão:

- **`status IN ('reserved', 'expired')`** cobre o caso de borda: se o token ainda é o
  mesmo (ninguém reabriu a célula), o pagamento é honrado mesmo que o job de expiração
  já tenha rodado — o token é a prova real de posse, não o status.
- **Distinção entre duplicata e conflito real:** se o `UPDATE` não encontrar linha, o
  código verifica se é porque o `payment_id` já foi gravado antes (retry inofensivo) ou
  porque o `token` não bate mais (a célula foi reaberta por outra pessoa nesse meio
  tempo — cenário raro, mas precisa de revisão manual em vez de falhar silenciosamente).
- **`payment_id UNIQUE`** garante que, mesmo se o webhook chegar duas vezes com o
  mesmo `paymentId`, o segundo processamento não sorteia um prêmio novo nem reenvia
  e-mail.
- **Transação (`BEGIN`/`COMMIT`)** garante que `status = 'paid'`, `prize_id`, o
  espelhamento em `payments` e os lançamentos em `cash_ledger` são gravados juntos,
  atomicamente — nunca existe um estado onde um está salvo e o outro não.
- **`cash_ledger` nunca é escrito fora dessa transação** — se ficasse pra depois (ex:
  um job separado agregando `payments`), um crash entre o `COMMIT` do pagamento e a
  gravação do ledger deixaria o saldo de caixa incorreto sem nenhum sinal de erro.
  Gravar dentro da mesma transação elimina essa classe de bug (seção 9).
- **Estado `paid_pending_prize`** existe para dar visibilidade operacional: se um job
  de monitoramento encontrar células paradas nesse status por mais que alguns
  segundos, é sinal de crash no meio da transação e precisa de investigação manual
  (recuperação automática total é possível, mas exige um job de reconciliação
  separado — fora do escopo deste documento).
- **Envio de e-mail fica fora da transação** porque é uma chamada de rede externa
  lenta e sujeita a falha independente do banco; se falhar, o estado `paid` com
  `prize_id` já gravado permanece correto, e um job separado pode reprocessar apenas
  o envio de certificado (consultando `WHERE status = 'paid' AND certificate_sent_at
  IS NULL`).
- **Retornar `200 OK` mesmo em duplicata ou conflito** é importante — devolver erro
  faria o provedor continuar tentando reenviar um webhook que já foi tratado (mesmo
  que o tratamento, no caso de conflito, seja só registrar para revisão manual).

O sorteio do prêmio continua acontecendo **depois** da confirmação de pagamento, sempre
no servidor — nunca no front.

#### 4.4.4 A fila de revisão manual precisa de limite próprio

⚠️ **Correção:** a versão original chamava `alertarTimeDeOperacoes` uma vez por
ocorrência de `stale_token_conflict`, sem nenhum teto. Esse caminho é acionável por
qualquer pessoa que entenda o fluxo: reservar uma célula, deixá-la quase expirar, e
provocar reabertura por outro token bem na janela em que um pagamento de valor mínimo
está a caminho. Repetir isso não custa nada a mais pro atacante, mas cada ocorrência
gera uma notificação que exige atenção humana — em escala, isso não rouba células, mas
**satura a fila de operações**, criando ruído que pode encobrir outros abusos
acontecendo ao mesmo tempo.

`alertarTimeDeOperacoesComLimite` precisa, no mínimo:

- **Deduplicar por `cellId`** dentro de uma janela curta — se a mesma célula gerar
  `stale_token_conflict` mais de uma vez seguida, é o mesmo padrão se repetindo, não
  um novo caso; um único alerta (ou um alerta "agrupado" incrementando contador) basta.
- **Aplicar um teto de alertas individuais por período** (ex: no máximo N notificações
  diretas por hora); acima disso, os eventos continuam sendo gravados em
  `webhook_events` normalmente (a auditoria nunca para), mas a notificação em tempo
  real ao time vira um resumo agregado ("X conflitos nas últimas Y horas, ver
  `webhook_events`") em vez de um alerta por ocorrência.
- **Correlacionar com o `device_id`/IP da reserva que gerou o conflito** (disponível
  via `payments`, seção 8.4) — se o mesmo `device_id` aparece em múltiplos conflitos,
  isso é sinal mais forte de abuso deliberado do que de coincidência de timing, e pode
  alimentar o mesmo mecanismo de escalonamento para CAPTCHA/bloqueio da seção 3.1, não
  só gerar mais um ticket de revisão manual.

Esse limite protege a capacidade operacional do time, não a integridade dos dados — a
gravação em `webhook_events` (seção 8.3) continua acontecendo sempre, sem limite,
porque ela é a fonte de auditoria; o que muda é só a quantidade de notificações ativas
que chegam a uma pessoa.

### 4.5 Passo 4 — Expiração de reservas não pagas

Sem esse mecanismo, uma célula reservada e nunca paga ficaria bloqueada para sempre.

```sql
-- Job periódico (cron), roda a cada 30 segundos:
UPDATE cells
SET status = 'expired'
WHERE status = 'reserved'
  AND reserved_at < NOW() - INTERVAL '5 minutes';
```

- **Tempo de expiração:** 5 minutos.
- **Frequência do job:** recomendado rodar a cada 30s (mais frequente que o próprio
  intervalo de expiração), para não deixar a célula presa por tempo adicional além do
  prazo já vencido.
- **UX recomendada:** mostrar um contador visível no checkout (ex: "você tem 5:00 para
  concluir o pagamento"), para o usuário entender que a reserva não é permanente.

### 4.6 Reabertura de célula expirada

Removida como seção separada — a lógica de reabertura já está incorporada na query
única de reserva (seção 4.2). Não existe mais uma segunda query específica para esse
caso.

## 5. Resumo do fluxo completo (jornada de UI)

1. **Clique na célula** → abre um **modal** com um botão "Revelar".
   - Nenhuma reserva é criada ainda neste ponto — é só uma visualização.
2. **Clique em "Revelar"** → dispara a reserva no back:
   - `INSERT ... ON CONFLICT DO UPDATE ... WHERE status = 'expired'` (seção 4.2) —
     cria a célula se nunca existiu, ou reabre se estava `expired`, sempre gerando um
     token novo. Sujeito a rate limit por IP + `device_id`, com escalonamento para
     CAPTCHA em caso de abuso (seção 3.1).
   - Se falhar → célula já ocupada (`reserved`/`paid`), modal informa que não está mais
     disponível.
   - Se funcionar → back retorna `{ cellId, token }`; front guarda o `token` em estado
     (memória da aplicação, nunca em URL) e avança para a etapa de e-mail.
3. **Etapa de e-mail** (dentro do mesmo fluxo/modal) → usuário informa o e-mail
   (obrigatório).
   - Front envia `{ cellId, token, email }` no corpo do POST → back grava o e-mail na
     reserva, validando o `token`, e chama `criarCheckout` de forma idempotente
     (reaproveita cobrança `pending` existente em vez de duplicar — seção 4.3.1).
4. **Checkout de pagamento** → usuário é direcionado para pagar, com `cellId` e `token`
   vinculados ao checkout **via referência externa servidor-a-servidor**, nunca em
   parâmetro de URL visível ao navegador (seção 6).
   - Se não pagar em 5 minutos, a reserva expira e a célula é liberada (ver seção 4.5).
5. **Provedor de pagamento → Back (webhook)** → confirma o pagamento.
   - Back valida a **assinatura HMAC** do webhook.
   - Back valida `cellId` + `token` + idempotência via `payment_id`.
   - Numa transação: atualiza status para `paid_pending_prize` → sorteia o prêmio →
     grava `prize_id` → status final `paid`.
   - Envia o certificado para o e-mail informado (fora da transação, com reprocessamento
     possível se falhar).
6. **Modal de visualização da célula revelada** → front exibe o resultado final
   (célula revelada, com ou sem prêmio).

### Diagrama resumido

```
[Clique na célula]
       │
       ▼
[Modal: botão "Revelar"]
       │  clique em Revelar (rate limit IP + device_id; CAPTCHA se abuso)
       ▼
[Back: INSERT ou reabre se expired] ──falha──▶ [Modal: célula indisponível]
       │ sucesso (retorna token novo, guardado em memória — nunca em URL)
       ▼
[Etapa: informar e-mail] ──▶ [Back: UPDATE email (valida token)]
       │                           │
       │                           ▼
       │                  [criarCheckout idempotente:
       │                   reaproveita cobrança pending
       │                   ou cria uma nova]
       ▼
[Checkout de pagamento] ──expirou (5 min)──▶ [Back: status = expired, libera célula]
       │ pagamento confirmado (webhook, assinatura validada)
       ▼
[Back: token ainda bate? (reserved OU expired)]
       │ sim                              │ não (célula já reaberta por outro token)
       ▼                                  ▼
[paid_pending_prize] ──(transação)──▶     [registra conflito, aciona revisão manual]
[sorteia prêmio, status = paid]
       │
       ▼
[Envia certificado] ──falhou──▶ [job de reprocessamento por certificate_sent_at IS NULL]
       │ sucesso
       ▼
[Modal: célula revelada — resultado final]
```

## 6. Pontos de segurança importantes

- **O `id` da célula pode ser manipulado livremente pelo usuário** — isso não é uma
  falha, é apenas "qual célula ele quer reivindicar". O servidor é sempre a autoridade
  final sobre disponibilidade e resultado.
- **O sorteio do prêmio nunca pode ser calculado no front**, nem por fórmula
  determinística (ex: hash do id) — isso permitiria a qualquer pessoa calcular
  antecipadamente quais células têm os melhores prêmios antes mesmo de clicar.
- **A confirmação de pagamento deve vir de um webhook do provedor**, nunca de um
  parâmetro enviado pelo front após redirecionamento — evita que alguém simule "paguei"
  sem realmente ter pago.
- **A assinatura do webhook precisa ser validada** antes de qualquer escrita no banco —
  a URL do endpoint não é segredo suficiente.
- **O processamento do webhook precisa ser idempotente e atômico** — retries do
  provedor não podem sortear prêmio duas vezes nem travar a célula num estado
  intermediário quebrado.
- **A janela entre expiração e confirmação de pagamento precisa de tratamento
  explícito** (seção 4.4.3) — um pagamento pode chegar depois do job de expiração ter
  rodado; o `token`, não o `status`, é a prova real de que o pagamento pertence àquela
  reserva.
- **O endpoint de reserva precisa de rate limit em múltiplas camadas** — IP sozinho é
  contornável com proxy/VPN rotativo. `device_id` (fingerprint) soma-se ao IP como
  segundo sinal, e um padrão repetido de rate-limit acionado escalona para exigir
  CAPTCHA antes da próxima tentativa (seção 3.1).
- **O IP usado em rate limit e antifraude precisa vir de uma fonte confiável, não do
  `X-Forwarded-For` cru** — esse header é escrito pelo próprio cliente na origem; sem
  o proxy de borda sobrescrevê-lo (ou a aplicação saber quantos hops de proxy confiável
  existem na cadeia), qualquer requisição pode declarar o IP que quiser e todo o rate
  limit por IP da seção 3.1 vira decorativo (seção 8.4).
- **Rate limit por contador (IP, `device_id`) não pega rotação combinada dos dois
  sinais ao mesmo tempo** — um atacante que troca IP e device juntos a cada request
  passa despercebido por contadores isolados. É preciso uma camada adicional de
  detecção por padrão agregado (volume por faixa de IP/ASN, velocidade incompatível
  com uso humano, concentração em células "desejáveis" vindas de devices nunca vistos)
  que escale para CAPTCHA na faixa inteira, não só no IP/device individual (seção 3.1).
- **A fila de revisão manual de conflitos (`stale_token_conflict`, seção 4.4.3) precisa
  de teto e deduplicação próprios** — sem limite, é um caminho que um atacante pode
  forçar repetidamente sem custo adicional, saturando a capacidade de atenção do time
  de operações e criando ruído que pode encobrir outros abusos (seção 4.4.4).
- **O `reservation_token` nunca deve trafegar em query string ou qualquer parte visível
  de URL** — nem no link de checkout, nem em redirecionamentos. Um token em URL pode
  vazar pelo header `Referer` para o provedor de pagamento, ficar gravado em logs de
  servidor/analytics de terceiros, ou permanecer no histórico do navegador do usuário.
  O token só deve trafegar (a) no corpo (`body`) de requisições POST entre front e back,
  e (b) na referência externa embutida na cobrança Pix, enviada servidor-a-servidor
  entre o back e o provedor de pagamento (seção 4.3.1) — nunca como algo que o
  navegador exponha ou redirecione.
- **A criação de cobrança Pix precisa ser idempotente por reserva** — sem isso, um
  refresh de página, duplo clique ou retry de rede na etapa de e-mail gera múltiplas
  cobranças para a mesma célula, confundindo o usuário e abrindo espaço para pagamento
  duplicado por engano. `criarCheckout` deve verificar se já existe uma cobrança
  `pending` para aquele `cell_id` antes de criar uma nova (seção 4.3.1).
- **Sem autenticação de conta, o `reservation_token` faz esse papel de forma temporária**:
  é a única prova de que uma etapa posterior (informar e-mail, confirmar pagamento)
  pertence à mesma reserva originada pelo clique. Ele deve ser aleatório e
  não-adivinhável (UUID), nunca sequencial ou derivado do `id` da célula.

## 7. Superfície da API

Resumo de todos os endpoints necessários para implementar o fluxo descrito neste
documento, mais o job periódico de expiração. Nenhum deles ainda existe — hoje só
existe o front (`PixelGrid.jsx`).

### 7.1 `GET /api/cells`

Leitura do estado de um range de células, usada para popular o grid virtualizado
conforme o usuário rola a tela (seção 2.1).

- **Auth:** nenhuma — endpoint público, só leitura de estado visual.
- **Rate limit:** leve, mais por proteção de infraestrutura que por segurança.
- **Cache:** recomendado, poucos segundos (o estado muda pouco entre polls).

```
GET /api/cells?from=480000&to=480050
```

```json
// 200 OK
[
  { "id": 480000, "status": "available" },
  { "id": 480001, "status": "reserved" },
  { "id": 480002, "status": "paid" },
  ...
]
```

`expired` nunca aparece na resposta — é normalizado para `available` (seção 2.1).

### 7.2 `POST /api/cells/reserve`

Disparado ao clicar em "Revelar" no modal. Tenta reservar a célula — cria se nunca
existiu, ou reabre se estava `expired` (query unificada, seção 4.2).

- **Auth:** nenhuma.
- **Rate limit:** obrigatório, em múltiplas camadas (seção 3.1):
  - por IP (total de reservas ativas + tentativas por minuto);
  - por `device_id` (mesmo teto de reservas ativas simultâneas);
  - escalonamento para CAPTCHA quando um IP ou `device_id` acionar o limite repetidas
    vezes numa janela curta.

```json
// Request
POST /api/cells/reserve
{ "id": 480030, "deviceId": "fp_9a3c1e..." }
```

```json
// 200 OK — reserva bem-sucedida
{ "cellId": 480030, "token": "b3f1c2a0-...-uuid" }
```

```json
// 409 Conflict — já reservada/paga por outra pessoa
{ "error": "Célula já reservada ou revelada" }
```

```json
// 429 Too Many Requests — rate limit acionado
{ "error": "Muitas tentativas, aguarde e tente novamente" }
```

```json
// 428 Precondition Required — escalonado para CAPTCHA após abuso repetido
{ "error": "Verificação adicional necessária", "captchaRequired": true }
```

### 7.3 `POST /api/cells/email`

Etapa de e-mail do fluxo, associa o e-mail à reserva e gera (ou reaproveita) o link de
checkout (seção 4.3 e 4.3.1).

- **Auth:** validação via `token` (não é autenticação de conta, é prova de posse
  da reserva — seção 4).
- **Idempotência:** chamadas repetidas para a mesma reserva reaproveitam a cobrança
  Pix `pending` já existente, em vez de criar uma nova (seção 4.3.1). O `token` é
  sempre recebido no corpo da requisição, nunca em query string.

```json
// Request
POST /api/cells/email
{ "cellId": 480030, "token": "b3f1c2a0-...-uuid", "email": "usuario@example.com" }
```

```json
// 200 OK
{ "checkoutUrl": "https://checkout.provedor.com/sessao/xyz" }
```

```json
// 400 Bad Request — token inválido, reserva expirada, ou id/token não combinam
{ "error": "Reserva inválida, expirada ou token incorreto" }
```

### 7.4 `GET /api/cells/:id`

Detalhe de uma célula específica — usado quando o modal abre para exibir o
resultado de uma célula já paga (emoji, prêmio), não só o status genérico que vem
do endpoint de range (7.1).

- **Auth:** nenhuma — mesmo nível de exposição pública do estado do grid.
- Não substitui o `token`: este endpoint não permite nenhuma ação sobre a célula,
  só leitura do resultado já público (célula revelada é visível para qualquer
  visitante, é o conceito central do produto).

```json
// Request
GET /api/cells/480030
```

```json
// 200 OK — célula paga/revelada
{
  "id": 480030,
  "status": "paid",
  "emoji": "🌟",
  "prizeLabel": null
}
```

```json
// 200 OK — célula ainda disponível
{ "id": 480030, "status": "available" }
```

### 7.5 `POST /webhook/payment-confirmed`

Recebido do provedor de pagamento (Asaas/Stripe/etc.), nunca chamado pelo front
(seção 4.4).

- **Auth:** validação de assinatura HMAC do provedor — obrigatória antes de
  processar qualquer coisa (seção 4.4.1).
- **Idempotência:** garantida via `payment_id UNIQUE` + transação, incluindo o caso de
  borda entre expiração e confirmação (seção 4.4.3), e a criação de cobrança já é
  idempotente rio acima, na seção 4.3.1.
- **`cellId`/`token`:** não chegam como campos soltos no payload — são extraídos do
  campo de referência externa que o provedor devolve, o mesmo que foi embutido na
  criação da cobrança Pix (seção 4.3.1), sempre servidor-a-servidor, nunca via URL
  visível ao navegador. O formato exato do payload varia por provedor.

```json
// Request (exemplo ilustrativo — formato real depende do provedor escolhido)
POST /webhook/payment-confirmed
{
  "paymentId": "pay_abc123",
  "referenciaExterna": "{\"cellId\":480030,\"token\":\"b3f1c2a0-...-uuid\"}"
}
```

```
200 OK   — processado com sucesso, ou já processado antes (idempotente)
401      — assinatura inválida
500      — erro interno, provedor deve tentar novamente
```

Este endpoint nunca retorna dado nenhum sobre o prêmio sorteado no corpo da
resposta — o resultado só chega ao usuário pelo certificado por e-mail e pela
leitura pública em 7.4/7.1.

### 7.6 Job: expiração de reservas

Não é uma API — é um processo periódico (cron), descrito na seção 4.5.

- **Frequência:** a cada 30 segundos.
- **Ação:** `UPDATE cells SET status = 'expired' WHERE status = 'reserved' AND
  reserved_at < NOW() - INTERVAL '5 minutes'`.
- Não expõe endpoint HTTP — roda internamente no servidor/worker.

### 7.7 Resumo

| Endpoint | Método | Auth | Chamado por |
|---|---|---|---|
| `/api/cells` | GET | nenhuma | front (scroll do grid) |
| `/api/cells/reserve` | POST | rate limit (IP + device_id, CAPTCHA se abuso) | front (clique "Revelar") |
| `/api/cells/email` | POST | token | front (etapa de e-mail) |
| `/api/cells/:id` | GET | nenhuma | front (abrir modal de detalhe) |
| `/webhook/payment-confirmed` | POST | assinatura HMAC | provedor de pagamento |
| *(job de expiração)* | — | — | cron interno |

## 8. Estrutura de tabelas

Três tabelas cobrem o fluxo completo. A `cells` já estava definida (seção 4.1); as
outras duas ficaram implícitas até agora e precisam ser explicitadas.

### 8.1 `cells` — já definida, com um ajuste

A definição da seção 4.1 fica assim, com a referência explícita para `prizes`:

```sql
CREATE TABLE cells (
  id INT PRIMARY KEY,
  reservation_token UUID NOT NULL DEFAULT gen_random_uuid(),
  email TEXT,
  status TEXT NOT NULL DEFAULT 'reserved',
  -- reserved | paid_pending_prize | paid | expired
  reserved_at TIMESTAMP DEFAULT NOW(),
  payment_id TEXT UNIQUE,
  prize_id INT REFERENCES prizes(id),
  certificate_sent_at TIMESTAMP
);

-- índices necessários para as queries já descritas no doc:
CREATE INDEX idx_cells_status_reserved_at ON cells (status, reserved_at);
-- ↑ usado pelo job de expiração (seção 4.5) e pela leitura de range (seção 2.1)
```

### 8.2 `prizes` — catálogo de prêmios

Necessária porque `sortearPremio()` (seção 4.4.3) precisa de uma fonte real de onde
sortear, com pesos e controle de estoque — hoje isso é só uma função mencionada, sem
tabela por trás.

```sql
CREATE TABLE prizes (
  id INT PRIMARY KEY,
  label TEXT NOT NULL,           -- ex: "R$ 50 de crédito", "Camiseta", "Sem prêmio"
  weight INT NOT NULL,           -- peso relativo no sorteio (maior = mais comum)
  stock INT,                     -- NULL = ilimitado; número = quantidade restante
  value_cents INT NOT NULL DEFAULT 0,  -- custo real do prêmio para o caixa, em centavos
                                        -- (valor de crédito, custo de aquisição do item
                                        -- físico, etc.); 0 para "Sem prêmio". Usado pelo
                                        -- monitoramento de caixa da seção 9.
  active BOOLEAN NOT NULL DEFAULT true
);
```

- `sortearPremio()` deve considerar apenas prêmios `active = true` e com `stock IS NULL
  OR stock > 0`, fazendo o sorteio ponderado por `weight`.
- Se o sorteio resultar num prêmio com `stock` finito, o decremento do estoque precisa
  acontecer **dentro da mesma transação** do webhook (seção 4.4.3) — senão dois
  sorteios simultâneos podem entregar o último item em estoque duas vezes.
- Vale sempre ter um prêmio tipo "Sem prêmio" com peso alto — reforça que nem toda
  célula paga precisa premiar, dependendo do modelo de negócio.
- **`value_cents` é o que permite calcular o total distribuído em prêmios** (seção 9).
  É um valor de negócio, não decorativo: para créditos e prêmios em dinheiro é o valor
  de face; para itens físicos, deve refletir o custo real de aquisição, não o preço de
  varejo — é isso que sai do caixa, não o que o item "vale" para o usuário.

### 8.3 `webhook_events` — auditoria de webhooks recebidos

Não é estritamente necessária para o fluxo funcionar (a idempotência já é garantida
por `payment_id UNIQUE` na própria `cells`, seção 4.4.3), mas é fortemente recomendada
para debugging e resolução de disputas ("paguei e não recebi certificado").

```sql
CREATE TABLE webhook_events (
  id BIGSERIAL PRIMARY KEY,
  payment_id TEXT NOT NULL,
  cell_id INT,
  payload JSONB NOT NULL,        -- corpo bruto recebido, para auditoria
  signature_valid BOOLEAN NOT NULL,
  result TEXT NOT NULL,          -- processed | duplicate | invalid_signature | error
  received_at TIMESTAMP DEFAULT NOW()
);

CREATE INDEX idx_webhook_events_payment_id ON webhook_events (payment_id);
```

- Toda chamada recebida em `/webhook/payment-confirmed` (seção 7.5) grava uma linha
  aqui, **mesmo quando rejeitada por assinatura inválida ou duplicata** — é esse
  histórico que permite investigar "o provedor mandou o webhook e a gente ignorou por
  quê" sem depender de log de aplicação, que costuma rotacionar/expirar.
- Não faz parte da transação principal do pagamento (seção 4.4.3) — pode ser gravado
  antes ou depois, é só auditoria, não deve bloquear nem falhar o processamento real.

### 8.4 `payments` — detalhe financeiro, histórico de tentativas, antifraude e idempotência de checkout

A `cells.payment_id` (seção 8.1) guarda só a referência ao pagamento **confirmado** —
suficiente para o fluxo de reserva funcionar. Mas o checkout pode gerar múltiplas
tentativas antes de confirmar, e dados financeiros/antifraude não pertencem
naturalmente à tabela que representa o estado da célula. Por isso, uma tabela própria.

⚠️ **Correção:** a coluna `checkout_url` foi adicionada para viabilizar a idempotência
de `criarCheckout` (seção 4.3.1) — sem ela, não haveria como devolver a mesma URL numa
segunda chamada sem re-consultar o provedor.

```sql
CREATE TABLE payments (
  id BIGSERIAL PRIMARY KEY,
  cell_id INT NOT NULL REFERENCES cells(id),
  provider_payment_id TEXT NOT NULL UNIQUE,  -- id do pagamento no provedor
  checkout_url TEXT NOT NULL,                -- reaproveitada em chamadas repetidas (seção 4.3.1)
  amount_cents INT NOT NULL,
  currency TEXT NOT NULL DEFAULT 'BRL',
  status TEXT NOT NULL,           -- pending | confirmed | failed | refunded

  -- antifraude: capturado no momento em que o checkout é criado
  device_id TEXT,                 -- fingerprint gerado no front (ex: FingerprintJS) —
                                   -- o mesmo device_id já deve ter sido enviado antes,
                                   -- em POST /api/cells/reserve (seção 3.1 e 7.2)
  ip_address INET NOT NULL,
  user_agent TEXT,
  geo_country TEXT,               -- derivado do IP, no servidor — nunca do cliente
  geo_region TEXT,
  geo_city TEXT,

  created_at TIMESTAMP DEFAULT NOW(),
  confirmed_at TIMESTAMP
);

CREATE INDEX idx_payments_cell_id ON payments (cell_id);
CREATE INDEX idx_payments_ip_address ON payments (ip_address);
CREATE INDEX idx_payments_device_id ON payments (device_id);
-- índice parcial usado pela checagem de idempotência em criarCheckout (seção 4.3.1):
CREATE INDEX idx_payments_cell_pending ON payments (cell_id) WHERE status = 'pending';
```

**Método fixo em Pix:** como o produto aceita só Pix, não existe coluna `method` — se
algum dia for aceito outro meio de pagamento, aí sim vale adicionar a coluna de volta.

**Por que a localização precisa ser derivada no servidor, não enviada pelo cliente:**
qualquer coordenada de geolocalização que o front envie (`navigator.geolocation`, GPS do
dispositivo) pode ser falsificada trivialmente antes de chegar na API. A forma confiável
é o **servidor** pegar o `ip_address` da própria requisição HTTP e resolver
país/região/cidade via um serviço de geolocalização por IP (ex: MaxMind, ipapi) — o
cliente nunca é a fonte desse dado, só o transporte que carrega o IP até o back.

⚠️ **Correção crítica:** `req.headers['x-forwarded-for']` **não é confiável por padrão**.
Esse header é escrito pelo cliente na requisição original — se o proxy/load balancer
da infraestrutura só **anexar** o IP real ao final da lista, em vez de **substituir**
qualquer valor que já veio do cliente, um atacante pode mandar
`X-Forwarded-For: 1.2.3.4` manualmente e o back lê `1.2.3.4` como se fosse o IP dele,
já que o código pega o primeiro item da lista (`.split(',')[0]`). Isso não é uma falha
teórica: se esse ponto não estiver fechado, todo o rate limit por IP da seção 3.1 —
e a checagem de conflito de `ip_address` em `payments` — vira decorativo, porque cada
requisição pode declarar o IP que quiser. Esse ponto sustenta a defesa inteira da
seção 3.1, então precisa de tratamento explícito, não só o parsing ingênuo do header.

A extração de IP confiável depende de **onde** o parsing acontece:

- **Camada de infraestrutura (preferível):** configurar o proxy/load balancer (ex:
  Nginx, Cloudflare, AWS ALB) para **sobrescrever** `X-Forwarded-For` com o IP real da
  conexão TCP, descartando qualquer valor que o cliente tenha enviado antes de chegar
  no proxy. Nesse cenário, o header que chega na aplicação já é confiável por
  construção, e o back só precisa ler o **último** IP da cadeia (o mais próximo da
  infraestrutura), não o primeiro — o primeiro item continua sendo o que o cliente
  declarou.
- **Camada de aplicação (se não houver controle sobre o proxy):** usar uma lib que
  conheça a topologia de proxies confiáveis (ex: `app.set('trust proxy', N)` no
  Express, configurando quantos hops de proxy confiável existem na cadeia) em vez de
  pegar `.split(',')[0]` cegamente. Isso faz o framework descartar os IPs que vieram
  antes dos proxies conhecidos e devolver só o IP que efetivamente bateu na borda da
  infraestrutura.

```js
// no handler que cria o checkout, no back — nunca no front
//
// req.ip aqui assume que o framework já está configurado para confiar só nos
// proxies conhecidos (ex: `app.set('trust proxy', 1)` para 1 hop de load balancer)
// — não usar x-forwarded-for cru sem essa configuração.
const ip = req.ip;
const geo = await geolocationService.lookup(ip); // resolve no servidor

await db.query(
  `INSERT INTO payments (cell_id, provider_payment_id, checkout_url, amount_cents,
                          status, device_id, ip_address, user_agent,
                          geo_country, geo_region, geo_city)
   VALUES ($1, $2, $3, $4, 'pending', $5, $6, $7, $8, $9, $10)`,
  [cellId, providerPaymentId, checkoutUrl, amountCents, deviceId, ip,
   req.headers['user-agent'], geo.country, geo.region, geo.city]
);
```

- Toda tentativa de checkout (mesmo as que falham) gera uma linha aqui — não só a que
  confirma. Isso dá visibilidade do funil e também um histórico útil pra investigar
  padrões suspeitos (mesmo `device_id` ou `ip_address` tentando muitas reservas em
  sequência, por exemplo).
- **Idempotência de criação:** antes de inserir uma nova linha, `criarCheckout`
  consulta se já existe uma linha `status = 'pending'` para aquele `cell_id` e, se
  existir, devolve `checkout_url` dessa linha em vez de chamar o provedor de novo
  (seção 4.3.1). O índice parcial `idx_payments_cell_pending` existe especificamente
  para essa consulta.
- Quando o webhook confirma um pagamento (seção 4.4.3), a transação atualiza tanto
  `payments.status = 'confirmed'` quanto `cells.status = 'paid'` e `cells.payment_id`
  — as duas tabelas ficam sincronizadas dentro da mesma transação.
- `provider_payment_id UNIQUE` aqui reforça a mesma idempotência que já existe via
  `cells.payment_id UNIQUE` — redundante de propósito, os dois lados protegem contra
  duplicata.
- Reembolso (`refunded`) e qualquer lógica de estorno ficam isolados nessa tabela, sem
  precisar mexer no estado da célula (que continua `paid` — a célula já foi entregue,
  o reembolso é uma questão financeira à parte).
- **`device_id` é capturado já em `POST /api/cells/reserve`** (seção 7.2), antes mesmo
  do checkout, e reutilizado aqui — isso alimenta diretamente o rate limit por
  `device_id` da seção 3.1 com um dado mais estruturado do que só o IP da requisição,
  e permite cruzar reservas e tentativas de pagamento do mesmo dispositivo mesmo
  quando o IP muda entre uma etapa e outra.

### 8.5 O que fica de fora do banco (de propósito)

- **Rate limit de reservas** (seção 3.1) — não vira tabela SQL. Fica em cache
  (Redis, com TTL) por natureza: é estado de curtíssimo prazo, de alta frequência de
  escrita, e não precisa durabilidade além da janela de rate limit. Isso vale tanto
  para os contadores por IP quanto por `device_id`, e para o flag de "exige CAPTCHA"
  de um IP/device que acionou o limite repetidas vezes.
- **Contagem de colunas lógicas** (`LOGICAL_COLUMNS`, seção 1.1) — é constante de
  aplicação compartilhada entre front e back, não dado de banco.

### 8.6 Resumo

| Tabela | Propósito | Obrigatória? |
|---|---|---|
| `cells` | Estado de cada célula, reserva, pagamento, prêmio | Sim |
| `prizes` | Catálogo de prêmios para o sorteio ponderado, com custo em `value_cents` | Sim |
| `payments` | Histórico de tentativas, idempotência de checkout, antifraude | Recomendada, forte para idempotência |
| `webhook_events` | Log de auditoria de webhooks recebidos | Recomendada, não bloqueante |
| `cash_ledger` | Livro-razão de movimentações de caixa (receita, prêmios, reembolsos) | Sim, para monitoramento financeiro (seção 9) |

## 9. Monitoramento financeiro: caixa, receita e prêmios distribuídos

O objetivo é responder três perguntas de forma confiável: quanto entrou (receita
confirmada), quanto saiu em prêmios, e qual é o saldo de caixa atual. Nenhuma das
tabelas existentes até aqui cobre isso sozinha: `payments` tem o valor recebido por
tentativa, mas não distingue "confirmado" de "ainda pendente" numa view agregada
pronta; `prizes`/`cells` têm o prêmio sorteado, mas (antes da seção 8.2) não tinham
valor monetário nenhum associado.

### 9.1 Por que um ledger dedicado, e não só agregar `payments`/`cells`

Seria possível calcular tudo isso com `SUM(amount_cents) FROM payments WHERE status =
'confirmed'` e um `JOIN` de `cells` com `prizes` somando `value_cents`. Isso funciona,
mas tem duas limitações que crescem com o tempo:

- **Fica caro conforme o volume cresce.** Toda consulta de saldo escaneia (ou agrega
  via índice) a tabela inteira de pagamentos e a tabela inteira de células pagas. Um
  ledger append-only já nasce no formato de "evento financeiro", então relatórios por
  período (dia, semana, mês) são só um `WHERE created_at BETWEEN ...` sobre uma tabela
  mais enxuta e já filtrada para eventos que de fato movimentam caixa.
- **Não tem lugar natural para reembolsos e ajustes.** `payments.status = 'refunded'`
  (seção 8.4) marca que um reembolso aconteceu, mas não registra isso como uma
  movimentação de caixa própria — e ajustes manuais (ex: estorno parcial, correção de
  um lançamento errado) não têm onde morar em `payments` ou `cells` sem forçar a
  semântica dessas tabelas, que representam **estado**, não **histórico de
  movimentação**.

O `cash_ledger` separa essas duas responsabilidades: `cells`/`payments`/`prizes`
continuam sendo a fonte de verdade sobre o **estado** de cada célula/pagamento; o
ledger é a fonte de verdade sobre **o que efetivamente moveu o caixa**, como uma
lista de lançamentos que nunca são alterados, só adicionados — o mesmo princípio de
log append-only que você já usa no motor de precificação do P2P lending.

### 9.2 Estrutura

```sql
CREATE TABLE cash_ledger (
  id BIGSERIAL PRIMARY KEY,
  entry_type TEXT NOT NULL,        -- 'revenue' | 'prize_payout' | 'refund'
  cell_id INT NOT NULL REFERENCES cells(id),
  amount_cents INT NOT NULL,       -- sempre positivo; entry_type define a direção
  created_at TIMESTAMP DEFAULT NOW()
);

-- idempotência: no máximo um lançamento de cada tipo por célula.
-- 'revenue' e 'prize_payout' são naturalmente 1-por-célula (preço fixo, um prêmio
-- por célula). 'refund', se algum dia precisar ser parcial/múltiplo, exige revisar
-- essa constraint (ver 9.4).
CREATE UNIQUE INDEX idx_cash_ledger_dedup ON cash_ledger (entry_type, cell_id);

-- usado pelos relatórios por período (9.3)
CREATE INDEX idx_cash_ledger_type_created ON cash_ledger (entry_type, created_at);
```

- **`amount_cents` é sempre positivo** — a direção do movimento (entrada ou saída) vem
  do `entry_type`, nunca do sinal do número. Isso evita o erro clássico de somar tudo
  direto e obter um resultado errado se algum lançamento for gravado com o sinal
  trocado por engano.
- **Nunca existe `UPDATE` nem `DELETE` nessa tabela** — se um lançamento estiver
  errado, a correção é um novo lançamento compensatório (ex: um `refund` que anula um
  `revenue`), nunca editar a linha original. Isso preserva o histórico completo para
  auditoria, igual ao princípio de log append-only já usado nas outras partes do
  sistema.
- **`ON CONFLICT DO NOTHING`** na escrita (seção 4.4.3) é a rede de segurança: mesmo
  que o webhook seja reprocessado por algum motivo fora do fluxo normal de
  idempotência já existente, o ledger nunca duplica um lançamento para a mesma célula.

### 9.3 Consultas

**Saldo de caixa atual:**

```sql
SELECT
  COALESCE(SUM(amount_cents) FILTER (WHERE entry_type = 'revenue'), 0)
  - COALESCE(SUM(amount_cents) FILTER (WHERE entry_type = 'prize_payout'), 0)
  - COALESCE(SUM(amount_cents) FILTER (WHERE entry_type = 'refund'), 0)
  AS saldo_caixa_cents
FROM cash_ledger;
```

**Receita total confirmada:**

```sql
SELECT COALESCE(SUM(amount_cents), 0) AS receita_total_cents
FROM cash_ledger
WHERE entry_type = 'revenue';
```

**Total distribuído em prêmios:**

```sql
SELECT COALESCE(SUM(amount_cents), 0) AS premios_distribuidos_cents
FROM cash_ledger
WHERE entry_type = 'prize_payout';
```

**Qualquer um dos três por período** (dashboard diário/semanal/mensal), usando o
índice `idx_cash_ledger_type_created`:

```sql
SELECT
  date_trunc('day', created_at) AS dia,
  entry_type,
  SUM(amount_cents) AS total_cents
FROM cash_ledger
WHERE created_at >= NOW() - INTERVAL '30 days'
GROUP BY 1, 2
ORDER BY 1, 2;
```

Para volumes muito altos (dezenas de milhões de lançamentos), essas agregações podem
ficar lentas mesmo com índice. Se isso acontecer na prática, o próximo passo natural é
uma tabela de resumo diário (`cash_ledger_daily_summary`, uma linha por dia/tipo,
atualizada por um job) — mas não vale adicionar essa complexidade agora, antes de o
volume real justificar.

### 9.4 Reembolsos — fora do escopo deste documento, mas o ledger já está pronto

O fluxo de reembolso em si (quem aciona, se é automático ou manual, como o provedor
Pix processa a devolução) não está definido em nenhuma seção anterior — `payments`
seção 8.4 só prevê o status `refunded` como destino possível, sem processo descrito.
Quando esse fluxo for desenhado, o ponto de integração com o caixa é direto: o mesmo
handler que marcar `payments.status = 'refunded'` deve, na mesma transação, inserir um
lançamento `entry_type = 'refund'` no `cash_ledger` com o valor devolvido — seguindo
exatamente o padrão já estabelecido em 4.4.3 (estado e lançamento financeiro sempre
gravados juntos, atomicamente).

### 9.5 O que o ledger não substitui

- **Não substitui `webhook_events`** (seção 8.3) — o ledger registra só o que
  efetivamente moveu caixa; `webhook_events` registra toda tentativa de webhook,
  incluindo as rejeitadas por assinatura inválida ou os conflitos de token (seção
  4.4.4), que nunca geram lançamento financeiro.
- **Não substitui reconciliação com o provedor Pix.** O `cash_ledger` reflete o que o
  seu sistema *acredita* ter recebido/pago, com base nos webhooks processados. Uma
  divergência real (ex: o provedor reporta um valor diferente do que o webhook
  informou) só aparece comparando o ledger com o extrato do provedor — isso é
  reconciliação financeira, um processo separado, não algo que a existência do ledger
  resolve sozinha.
